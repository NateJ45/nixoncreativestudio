# ci-dataset

Scripts that keep the CI dataset (D1 `ncs-ci`, R2 `ncs-ci-media`, Worker `ncs-ci`) in line with a committed snapshot of production content, so it can be refreshed or rebuilt from nothing without hand-copied SQL. Design: `docs/CMS-DESIGN.md` section 2.3. How CI uses the dataset: `docs/TESTING.md`.

## What is here

| File                     | Role                                                                                                                                                                                                                                                |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `snapshot.mjs`           | Reads production through the `emdash` CLI login and writes `rows.sql` and `media.json`. Read-only.                                                                                                                                                  |
| `rebuild.mjs`            | Applies the snapshot to the CI resources. Refresh by default, `--from-scratch` to rebuild.                                                                                                                                                          |
| `lib.mjs`                | Shared helpers. The only place that can write, and it can only reach the `ncs-ci` resources.                                                                                                                                                        |
| `rows.sql`, `media.json` | GENERATED, committed. Do not edit by hand.                                                                                                                                                                                                          |
| `terms.json`             | Hand-edited. Which taxonomy terms each CI case study carries (the CLI cannot read per-entry terms).                                                                                                                                                 |
| `fixtures.sql`           | Hand-written. The options the site needs plus test-only rows production should not carry (none today: the test photo and the journal entries are in `ci-content/`).                                                                                 |
| `cms-fixtures.mjs`       | Builds the CMS collections and menus from `cms/schema` and `cms/content` (production has none yet).                                                                                                                                                 |
| `cms-media.json`         | GENERATED by `cms-fixtures.mjs`, committed. Repo-only images behind CMS entries (the About photos); `rebuild.mjs` uploads them to `ncs-ci-media` from the checkout.                                                                                 |
| `cms-rows.sql`           | GENERATED by `cms-fixtures.mjs`, committed. The CMS entries; applied after `rows.sql` and `fixtures.sql`.                                                                                                                                           |
| `ci-content/`            | Hand-written, CI-only entries (`<collection>.json`, `{ slug, data }` list, `$file` images allowed). PR 11's `photos.json` is the one test photo. Merged by `cms-fixtures.mjs` into the generated files; never reaches `cms/content/` or production. |

## Commands

```bash
npm run ci-dataset                 # refresh: apply rows.sql + fixtures.sql, copy R2 files, verify
npm run ci-dataset -- --dry-run    # print the plan, change nothing
npm run ci-dataset -- --from-scratch
npm run ci-dataset:snapshot        # re-read production, rewrite rows.sql + media.json
npm run ci-dataset:snapshot -- --check   # exit 1 if the committed snapshot is out of date
```

You need `wrangler login` as an account that owns the ncs-ci resources, and the `emdash` CLI logged in to production (`npx emdash login --url https://www.nixoncreativestudio.com`) for the snapshot only. The refresh needs no production login: it fetches media from the live site's public URLs.

## When to run which

- **Normal day:** nothing. CI reads the pinned snapshot. Edits Nathan makes in the production admin never reach CI.
- **A CMS PR adds a collection or needs new test content:** re-export the seed (`node scripts/export-seed-from-instance.mjs --url https://www.nixoncreativestudio.com`), run `npm run ci-dataset -- --from-scratch`, then `npm run ci-dataset:snapshot`, then `npm run ci-dataset` again and commit `seed/seed.json`, `rows.sql`, `media.json`. A plain refresh cannot apply a seed change: it stops with "ncs-ci has no table ..." and tells you to use `--from-scratch`.
- **CI data looks wrong or empty:** `npm run ci-dataset` (refresh). It is idempotent, so run it as often as you like.

## --from-scratch, step by step

1. Drops every table in `ncs-ci` (children before the tables they reference, FTS virtual tables first).
2. `CLOUDFLARE_ENV=ci npm run build` then `npx wrangler deploy` of the `ci` Worker.
3. Waits 30 s for the new Worker version to take over, then one GET of `/` so EmDash runs its migrations and applies `seed/seed.json`, then polls (up to 150 s) until every field and redirect in the seed is in D1. EmDash seeds in the background at about 2 s per collection, so the old flow stopped at "ncs-ci has no table ..." and needed a plain `npm run ci-dataset` a minute later; and a first request that landed on the PREVIOUS Worker version seeded the old schema (found 2026-10-03, PR 13: a new `case_studies` field had no column). The poll catches both: it either finishes or says the dataset was seeded from another version and to run `--from-scratch` again.
4. The refresh below.

**While it runs, CI previews have no data.** Do not start it while a PR is mid-CI.

## What a refresh does

1. Checks every table named in `rows.sql` exists in `ncs-ci`.
2. Runs `rows.sql` (deletes of rows not in the snapshot, then `INSERT OR REPLACE` for media, taxonomy terms, content rows and term links), then `fixtures.sql`.
3. For each file in `media.json`: skips it when `ncs-ci-media` already holds an object of the same key and size, otherwise downloads it from `https://www.nixoncreativestudio.com/_emdash/api/media/file/<key>`, checks size and SHA-1 against `media.json`, and uploads it.
4. GETs `/`, `/work/`, every CI case study, and every media file through the CI Worker, and exits 1 on any miss.

## Safety

- Nothing here can write to production. `lib.mjs` has no helper for production D1 or R2, refuses any D1 name other than `ncs-ci`, and checks `wrangler.jsonc` `env.ci` still names the same resources before running.
- Production is read only through the `emdash` CLI login and public media URLs.
- Media keep production's storage keys, so an R2 copy is a straight copy under the same key. The 15 objects the hand-built dataset had under its own keys were deleted once, by hand, after the first from-scratch rebuild.
- Never run `wrangler deploy` without `CLOUDFLARE_ENV=ci`. `--from-scratch` sets it for you.

## CMS collections and menus (CMS-DESIGN PR 4 onwards; PR 5 added `pricing_tiers` and `pricing_addons`, PR 6 added `page_home`, PR 7 added `page_services` and `service_offerings`, PR 8 added `page_about` and the first images, PR 9 added `page_contact`, PR 10 extended the existing template `pages` collection for Privacy, Accessibility and Colophon, PR 11 added `page_work`, `page_photography`, `page_journal`, `page_not_found` and the `photos` collection with its one CI test photo, PR 12 extended the template `posts` collection (the Journal) with a published and a draft CI entry)

Production cannot be read for these until the main session loads them (it needs an admin token), so CI gets them from the committed sources instead: `node scripts/ci-dataset/cms-fixtures.mjs` merges every `cms/schema/<collection>.mjs` and `cms/content/menus.json` into `seed/seed.json` and writes the entries to `cms-rows.sql` (`--check` exits 1 when either is out of date; `src/lib/ciFixtures.test.ts` runs the same check). Because the schema lands through the seed, a new collection or menu needs `npm run ci-dataset -- --from-scratch`; an edit to an existing entry needs only a plain `npm run ci-dataset`. Once production holds a collection, add it to `PRODUCTION_HAS` in `cms-fixtures.mjs` and `snapshot.mjs` (which already lists it in `SNAPSHOT_ALL`) becomes the source of its rows. **Since 2026-10-03 production holds** site_settings, menus, pricing_addons, pricing_tiers, page_about, page_contact, page_home, page_journal, page_not_found, page_photography, page_services, page_work, service_offerings and pages (all in `PRODUCTION_HAS`, with `pages` added to `SNAPSHOT_ALL`), plus the schema only of photos and posts, which stay OUT of `PRODUCTION_HAS` because CI's test photo and journal entries are hand-written in `ci-content/`. `case_studies` is in `PRODUCTION_HAS` too (its rows were always the snapshot's; `cms/schema/case_studies.mjs` exists only so the production loader can add the PR 13 fields). Mind that `--from-scratch` requests `/` before the rows exist, and the route cache keeps that empty page for 5 minutes, so wait it out before a parity capture.

**CI-only test content (PR 11).** A collection production starts empty (`photos`) has a schema in `cms/schema/` and no file in `cms/content/`; `cms-fixtures.mjs` still puts it in the seed so the table exists. Its test rows live in `ci-content/<collection>.json` and are merged into `cms-rows.sql` and `cms-media.json`. `NCS_CI_NO_TEST_CONTENT=1 node scripts/ci-dataset/cms-fixtures.mjs` leaves them out and makes the generated SQL `DELETE FROM ec_photos;`, so a refresh returns the table to zero rows (how the empty `/photography/` is measured on the same data). Run the script again without the variable, and refresh, to restore them (the same variable empties the journal: `ci-content/posts.json` holds a PUBLISHED entry, `ci-test-entry`, and a DRAFT, `ci-draft-entry`; an entry can carry `"status": "draft"`, which writes no publish date, and `"terms": { "tag": [{ "slug", "label" }] }`, which writes the term and its link, clearing only ids that start `01CI`; run the suites with `JOURNAL_EMPTY=1` against that state); commit only the default output (`ciFixtures.test.ts` fails otherwise). A collection with no entries at all clears its table instead of writing an invalid `NOT IN ()`.

**Images in entries.** A `{ "$file": "src/assets/..." }` in `cms/content/<collection>.json` becomes a `media` row (in `cms-rows.sql`) plus an entry in `cms-media.json`; the entry stores the EmDash image value pointing at it. The refresh uploads the file with the same skip-if-present rule as production media and checks size and SHA-1 first.

**Redirects and the hero scene (PR 13).** `cms/content/redirects.json` is merged into `seed/seed.json` as EmDash redirect rows (`seedRedirects` in `cms-fixtures.mjs`; EmDash applies the seed on the first request, so it needs `--from-scratch`). `snapshot.mjs` sets `in_hero` and `hero_order` on the CI case studies named in `cms/content/case_studies.json` (production does not hold the fields until the PR 13 load). Two environment switches reproduce production's state today and are never committed: `NCS_CI_NO_REDIRECTS=1 node scripts/ci-dataset/cms-fixtures.mjs` leaves the redirect rows out (the code fallback in `src/lib/redirectFallback.ts` answers), and `NCS_CI_NO_HERO=1 npm run ci-dataset:snapshot` leaves the hero fields out (the hero uses its bundled five). Mind that a from-scratch rebuild requests `/` before the rows exist, so redeploy the same dist (`CLOUDFLARE_ENV=ci npx wrangler deploy`) to clear the route cache before a parity capture.

## Adding a case study to CI

1. Add the slug to `CASE_STUDY_SLUGS` in `snapshot.mjs`, and an entry to `terms.json`.
2. Add the slug to `caseStudySlugs` in `tests/routes.ts`.
3. `npm run ci-dataset:snapshot`, then `npm run ci-dataset`.

## Adding a collection to the snapshot

The design's singleton and list collections are already in `SNAPSHOT_ALL` in `snapshot.mjs` and are skipped (with a note in `rows.sql`) until they exist in production. A collection not listed there needs one line added. Fixtures for collections production should not carry (`photos`, journal `posts`) go in `ci-content/<collection>.json` (see above).

## Known limits

- Taxonomy links are pinned in `terms.json` because the CLI cannot read per-entry terms. If a case study's tags change in production, CI keeps the old ones until `terms.json` is edited.
- `emdash:site_id` and `emdash:seed_complete` are minted by EmDash on first run, so a `--from-scratch` gives the dataset a new site id. Nothing depends on it.
- The refresh deletes case study rows that are not in the snapshot, but leaves unrelated tables (comments, 404 log, schedulers) alone.
